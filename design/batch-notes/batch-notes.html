Decisions of the board (fru-notes-edit, 2026-10-28)

The ticket gave a title and no text. The agent decided each choice, the simplest and the safest, as the orchestrator asked. Each one can be changed by Mathieu.

  1. The choice is made when the notes are sent, in the group of the list, not in the composer. A note is kept one at a time; how several arrive is a question about all of them, asked once, at the one button that sends them. The composer keeps its two actions of FRU-124.
  2. Two choices, and today's is the default. « One issue for each note, under one parent » is what createBatch of Linear writes now: a person who does not read the choice gets what they got before. A third choice (one issue each, no parent) is left out: it is the plain « Send » of each note.
  3. Only where the place can group the notes. Linear today. Kept in Fruitback, an address, GitHub: no choice, and one line says why (frame F). The worker says it in the read, beside batch: batch: { max, maxBytes, groups: ['parent', 'one'] }; a worker of before says nothing and the widget shows frame A.
  4. An optional title, for the parent or for the one issue. Empty: the worker writes « N notes on /page ». It is typed by a person and goes to the tracker as text.
  5. One issue with every note keeps a pin for each note. Each note keeps its element; the pins share the stage of the issue. The thread says « Note 2 of 3 in ENG-143 ». A verdict, a reply or an edit acts on the issue, and the thread says so.
  6. One issue is all or nothing. It is one write; there is no half-sent case. Under a parent, the 207 of today stays (frame G).
  7. The choice is remembered for the tab, next to the drafts (sessionStorage), never for the account: it is a way of working on a page today.
  8. No picker of an existing issue (« add these notes to ENG-120 »). It would need a search of the tracker from the page, a new read with its own rights. Left as an open question below.

For the build, and the open questions

  1. Contract. One issue with several notes needs the description to hold several JSON blocks, and parseNoteFromDescription to answer several notes for one issue. The read then answers one issue for each note, with the same id and identifier, and a new optional field group: { index, count } for the thread. NOTE_VERSION does not move if the block of each note is unchanged.
  2. Worker. POST /feedback with an array takes ?group=one|parent&title=… (a query, as ?destination=, because the relay of the extension carries no other header). createBatch of Linear gets the mode. The memory of a batch (FRU-195) keys the one issue as it keys a parent.
  3. Widget. The group of the list (sidebar.ts) gets the fieldset; sendDrafts passes the mode; cutIntoRequests must keep the notes of one issue in one request, so « one issue » is offered only up to batch.max notes.
  4. Open: a note added later to the same issue (« same issue » for a note sent alone, from the composer). Not drawn: it needs to name an issue from the page.
  5. Open: GitHub sub-issues. The connector could write them (FRU-359 uses the App); then frame B applies to GitHub too.
